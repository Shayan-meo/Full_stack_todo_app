# Evolution of Todo – Hackathon II Constitution
<!-- Spec-Driven, Cloud-Native AI System -->

## Core Principles

### I. Spec-Driven First (NON-NEGOTIABLE)
No source code may be written or edited manually. Every change must originate from a corresponding specification file and be generated by Claude Code.

**Rationale**: This ensures traceability, reproducibility, and prevents technical drift from approved designs.

### II. Architectural Thinking
The engineer acts as a system architect and product owner. Claude Code acts as the implementation engine that materializes approved specifications.

**Responsibilities**:
- Engineer: Define requirements, review specifications, approve designs
- Claude Code: Generate implementations, suggest architectural improvements, maintain quality

### III. Iterative Evolution (Forward-Compatible)
Each phase must remain forward-compatible with the next:
Console → Web → AI Chatbot → Cloud-Native Distributed System.

**Requirements**:
- APIs must be version-stable across phases
- Data models must support migration paths
- Architecture must accommodate scaling requirements

### IV. Quality Over Speed
Specifications must be refined until the generated implementation requires zero manual edits and fully satisfies acceptance criteria.

**Quality Gates**:
- All acceptance criteria met
- Zero manual code edits required
- All tests passing
- Security scans clean
- Performance budgets met

### V. AI-Native Design
From Phase III onward, natural-language task management must be implemented using OpenAI Agents SDK and MCP tools.

**Integration Points**:
- Natural language task creation
- Intelligent task prioritization
- Context-aware suggestions
- Agent-driven workflow automation

## Technology Standards

### Standardized Stack
- **Backend**: Python 3.11+ (3.13 permitted where compatible)
- **Package Management**: uv
- **API Framework**: FastAPI
- **ORM**: SQLModel
- **Frontend**: Next.js (App Router)

All stack choices must align with hackathon documentation and maintain consistency across phases.

### Documentation Requirements
Every phase must include:

1. **CLAUDE.md**: Claude Code instructions and behavioral guidelines
2. **README.md**: Setup instructions, architecture overview, usage guide
3. **Complete /specs folder**: Historical specification evolution including:
   - spec.md (requirements)
   - plan.md (architecture)
   - tasks.md (implementation tasks)

### Security & Authentication
- **Authentication**: JWT-based authentication using Better Auth (from Phase II onward)
- **Secrets Management**:
  - No hard-coded secrets
  - Environment variables for local development
  - Kubernetes secrets for cluster deployment
  - Dapr secret stores where applicable
- **Security Scanning**: All dependencies must pass security audits

### Verification Protocol
Every implementation must be verified against acceptance criteria:

1. **Functional Testing**: All features work as specified
2. **Integration Testing**: Components interact correctly
3. **Security Testing**: No vulnerabilities introduced
4. **Performance Testing**: Meets defined budgets
5. **Compatibility Testing**: Forward-compatible with next phase

## Constraints

### No Manual Coding
Manual edits to generated source code are strictly prohibited.

**Exceptions**: None. If generated code is insufficient, specifications must be refined and regenerated.

### Folder Structure
The project must follow the Spec-Kit monorepo structure:

```
/specs
  /features     - Feature specifications
  /api          - API contracts
  /database     - Data models
  /ui           - UI specifications
/history
  /prompts      - Prompt history records
  /adr          - Architecture decision records
/.specify
  /memory       - Constitution and project memory
  /templates    - Specification templates
  /scripts      - Automation scripts
```

### Timebox
Each phase must be completed and submitted by its respective Sunday deadline as defined in the hackathon timeline.

**Phase Schedule**:
- Phase I: Console Application
- Phase II: Web Application
- Phase III: AI Chatbot Integration
- Phase IV: Local Kubernetes Deployment (Minikube)
- Phase V: Cloud Deployment (DigitalOcean DOKS / GKE / AKS)

## Success Criteria

### Zero Plagiarism
All logic must be uniquely produced through spec-driven generation.

**Verification**:
- All code generated from project-specific specifications
- No copied implementations from external sources
- Unique architectural patterns and solutions

### Feature Completeness
All five core features must function correctly in every phase:

1. **Add Task**: Create new todo items
2. **Delete Task**: Remove existing items
3. **Update Task**: Modify task details
4. **View Tasks**: List and filter tasks
5. **Mark Complete**: Toggle completion status

### Deployment Readiness

#### Phase IV: Local Deployment
- Fully functional on Minikube
- All services containerized
- Database persistence configured
- Health checks operational

#### Phase V: Cloud Deployment
- Fully functional on DigitalOcean DOKS (or equivalent GKE/AKS)
- Production-grade configuration
- Monitoring and observability enabled
- Auto-scaling configured
- Disaster recovery tested

## Development Workflow

### Specification Process
1. **Requirements Gathering**: Define user needs and acceptance criteria
2. **Architectural Planning**: Design system structure and interactions
3. **Task Breakdown**: Create testable, incremental tasks
4. **Review & Approval**: Engineer approves specifications
5. **Generation**: Claude Code produces implementation
6. **Verification**: Test against acceptance criteria
7. **Documentation**: Update PHRs and ADRs

### Quality Gates
Before advancing to the next phase:

- [ ] All acceptance criteria met
- [ ] All tests passing (unit, integration, e2e)
- [ ] Security scan passed
- [ ] Performance benchmarks met
- [ ] Documentation complete
- [ ] ADRs created for significant decisions
- [ ] PHRs recorded for all development sessions

### Risk Mitigation
Top risks and mitigation strategies:

1. **Specification Ambiguity**: Use clarifying questions and iterative refinement
2. **Technical Debt**: Maintain forward compatibility and refactor specifications
3. **Timeline Pressure**: Prioritize core features, document trade-offs in ADRs

## Governance

### Constitution Authority
This constitution is binding across all phases and overrides any ambiguous or implicit assumptions during implementation.

### Amendment Process
Constitutional amendments require:
1. Documented rationale
2. Impact analysis
3. Engineer approval
4. Migration plan for existing specifications
5. Updated version number

### Compliance Verification
All development work must verify:
- Adherence to spec-driven process
- Compliance with technology standards
- Satisfaction of quality gates
- Documentation completeness

### Architectural Decision Records
Significant decisions must be documented when they meet ALL criteria:
- **Impact**: Long-term consequences on architecture
- **Alternatives**: Multiple viable options considered
- **Scope**: Cross-cutting influence on system design
